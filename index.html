Database Structure

What the current schema tells us about how the business evolved, and how the redesign fixes it without losing what already works.

What exists today

The current schema is sound in places — contacts, companies, and activity all follow reasonable relational patterns. The problems are concentrated in two spots, both the result of extending the system reactively over ~20 years rather than remodeling it.

  • Repeating groups — fields like proLoadType1/2/3 and proDeadAns1–7 hard-cap what should be an unlimited child list.
  • Activity scope creep — the activity log carries product-sample fields (actThickness, actPanelColor) that only apply to one specific interaction type.

The repeating load-type and question fields move into proper child tables keyed back to the project, removing the artificial 3-item / 7-item caps. The activity log gets a companion ActivitySampleRequest table so the core log stays generic again.

Technical decision

The current Master Matrix database is a legacy schema that's carried Access-era conventions (like the -1/0 boolean flags) for roughly two decades. The question isn't whether to leave it behind — it's what to replace it with, and that choice is made alongside the app framework decision in S-03, not in isolation. A current-generation SQL Server keeps existing T-SQL and schema logic largely intact if the app layer stays close to its current shape; moving to PostgreSQL only pays off if the app layer is also being rebuilt from scratch, since otherwise the migration cost is paid twice for no real gain.

Business decision

Confirm with Yvette whether a Job ever reverts to a Project (e.g. a signed contract falls through). If it happens in practice, the lifecycle model needs to support reversal, not just forward progression.

Known limitation

Historical Project→Job transition dates were never captured — only the current flag state. Migration can backfill a single snapshot per record, not a true history. Future transitions will be fully timestamped going forward.

Migration Strategy

The system is used every day. The plan keeps it fully operational throughout, and lets us prove the new platform works before anyone's workflow depends on it.

Approach: continuous sync, not a cutover night

Rather than a single high-risk migration event, the old database stays live and authoritative while a change-capture process continuously mirrors every update into the new, redesigned schema in the background.

stays live & authoritative
→
Change Data Capture

→
New Database
redesigned schema, validated in parallel
Both systems run simultaneously — the new one earns trust before anyone uses it live

Rollout order — lowest risk first

OrderModuleWhy this positionRisk
1Contacts & CompanyFew dependencies, easy to validate independentlyLow
2Marketing & ExpensesSelf-contained, moderate usage volumeMedium
3Activity LogHigh volume, but logic is now well-understoodMedium
4Projects & JobsCore of the business, most complex redesign — moves last, once the pipeline is provenHigh

How each module actually cuts over

  • Initial bulk copy — a one-time transformation pass moves everything that already exists in the old table into the new, redesigned schema for that module.
  • CDC + continuous reconciliation take over from there — CDC watches the old database's transaction log and automatically mirrors every live change into the new database from that point forward, while reconciliation runs continuously alongside it, comparing record counts and checksums between both systems and alerting on any drift rather than relying on a one-time check.
  • Rollback safety net — two possible ways to build it. Once a module cuts over, the old database needs to stay caught up in case a rollback is ever needed. Same two options as before apply here, just in reverse: reverse CDC (infrastructure mirrors changes from the new database back to the old one automatically) or dual-write (application code explicitly writes to both). We use reverse CDC — same reasoning as the forward direction: no application write logic to touch, and no risk of two writes disagreeing mid-transaction if one succeeds and the other fails.
Technical decision

Why freeze is still needed even with CDC and reconciliation running: CDC always has a small amount of replication lag — a fraction of a second to a few seconds. A freeze is a short, planned pause that lets that lag drain to zero before writes are pointed at the new database, closing the one window where a write could otherwise be lost.

Business decision

Define an acceptable freeze window for the final, highest-risk cutover (Projects & Jobs) — e.g. end-of-day Friday rather than mid-week — and agree on how far in advance sales reps and PMs are told their module is changing underneath them.

Non-negotiable

No module is considered "cut over" until the reconciliation job has run clean for an agreed validation window. Calendar time here is the honest cost of doing this safely — it is not something to compress to hit an arbitrary date.

API Layer

The piece that doesn't exist today — a single, governed front door to the data that every future front end, integration, and AI feature builds on.

Why this layer is missing today — and why it matters

The current front end talks directly to the database. Every business rule is scattered across app code, stored procedures, and triggers — which is a large part of why four years of vendor work got stuck: any change to the front end risks the database, and vice versa.

Technical decision

REST is the default recommendation — simpler to build, test, and reason about for this scope than GraphQL. Framework (e.g. Django REST Framework or Node/Express) should match whatever language the front end and migration scripts are already written in, to minimize context-switching for a small team.

Business decision

Decide what genuinely needs real-time behavior (activity logging, project status changes) versus what can run as a scheduled batch (leadership reporting exports) — this materially changes infrastructure cost and complexity.

Why this unlocks the AI ask

An AI agent should never query raw production SQL. Once it calls the same governed endpoints as the front end, "find similar past jobs" or "log this expense" becomes a safe, well-defined action instead of an open-ended risk.

Front End & AI

By this point the hard problems — data integrity, live migration — are solved. The remaining risk is adoption, not architecture.

Principle: replicate first, innovate second

The new interface should feel recognizable on day one — same information, same flow — even though the technology underneath is completely different. Redesigning the workflow and the technology at the same time is a common way modernization projects lose user trust.

Legacy Front End
remaining un-migrated modules
↔
New Front End
migrated modules, built on the API
Both interfaces coexist during the transition, matching the module rollout order from S-02

Where AI adds real value — introduced additively

  • Natural-language project search — "show me projects with GC Turner from last year," translated into the same API calls a person's filters would make.
  • Smart flags — surface contacts with no logged activity in 60+ days, or projects stalled at a status for an unusual length of time.
  • Expense auto-categorization — suggest a category from the description, person still confirms.

Each of these ships as an optional addition next to the existing way of doing things, not a replacement — adoption is earned, not assumed.

Technical decision

Front-end framework choice follows the API/backend decision from S-03 for stack consistency. A modern component framework (e.g. React) is recommended for the UI itself given the responsiveness expected of a daily-use tool.

Business decision

Per-module training sessions for sales, PM, and back-office staff, timed to each cutover — plus a named point of contact for support during each module's first few live weeks, when trust in the new system is won or lost.

Freeze window

The final, highest-stakes front-end cutover (Projects & Jobs) is scheduled during the same low-activity freeze window as its data migration counterpart in S-02 — front end and data risk are retired together, not separately.

The Bottom Line

Same plan, no jargon — for anyone in the room who wasn't tracking the acronyms on sheets 1 through 4.

What we're actually doing

We're replacing the guts of the CRM without turning it off. First we fix how the data is organized, so it isn't fighting itself anymore. Then we build a clean, controlled way for anything — the website you use every day, or an AI assistant later — to safely read and update that data. Last, we rebuild the screens people actually look at, matching how you already work before we change anything about it.

What stays the same for you, day to day

  • The system keeps working the whole time — nothing goes offline for this to happen
  • Your workflow looks and feels familiar at first, even though the technology underneath is new

Nothing breaks. Nothing disappears. It just gets easier to use — and ready for what's next, including the AI assistant we talked about.

SHEET AI-01 / 05

Find Similar Past Jobs

Type in what a new project looks like, and instantly see every similar job Swirnow has done — going back decades.

The problem today

When someone's estimating a new project, the only way to remember "didn't we do something like this a few years ago?" is to actually remember it. Twenty years of recorded projects are only useful if someone happens to recall the right example at the right moment.

What this fixes

An estimator asks in plain English — "find similar past jobs" — and gets back a real list of comparable projects Swirnow has actually built, instantly. No digging through old files, no relying on memory.

This turns one person's memory into something the whole team can use — new hires get the same institutional knowledge instantly that used to take years to build up.

Smarter Pricing

Know instantly what similar past projects actually sold for — before a quote goes out the door.

SHEET AI-03 / 05

Why Deals Win or Lose

Decades of "why we lost it" and "why we won it" — turned into patterns leadership can actually act on.

What this fixes

Every time a deal is lost or won, the reason gets written down — but nobody's ever had an easy way to look at all of those reasons together. This surfaces the patterns: certain types of projects losing more often, certain stages where deals tend to stall, and more.

This can work two ways — a quarterly trend report for leadership, or a live nudge for sales reps while they're still working a deal. Worth deciding which matters more first.

The pattern-finding itself is standard database analysis, not AI — grouping and comparing reasons across every project, run directly on Swirnow's own server. AI only gets used at the very end, to turn the finding into a plain-language summary, or to help read reasons that were written as free text instead of picked from a fixed list.

SHEET AI-05 / 05

Know This Client's Slow Spots

Look at everything Swirnow has done with a client before, spot which steps always seem to take them longer, and prepare for it this time.

What this fixes

Some clients are just slower at certain steps — one always takes weeks to sign a contract, another is always late sending drawings. Right now that knowledge lives in whoever's worked with them before. This looks at a client's actual project history and flags their typical slow points before a new project even gets there.

How it plays out

A new project starts with this client. Before the "Contract Sent" stage even begins, the system already knows — from their past three projects — that this stage usually takes them twice as long as most clients. The PM gets a heads-up early, instead of finding out three weeks in that things have gone quiet again.

This gets sharper the more history is available. It works best for repeat clients with a real track record — for a brand-new client, there's nothing to learn from yet, so this feature naturally improves as the new system captures more history over time.

Same mechanism as AI-03: comparing a client's stage timing against the norm is standard database analysis — a Python script for the more involved cross-referencing (client, stage, project type at once) — running on Swirnow's own server. AI only turns the finding into the plain-language heads-up the PM actually sees.

SHEET INF-01 / 04

Core Server & Staging

Fully on-premises, sized with real headroom — not just for today's CRM, but for what gets added on top of it later.

Why a 2-socket rackmount server, not a basic tower

A single-socket tower server (like a Lenovo ThinkSystem ST250 V3) would comfortably handle the CRM database alone. But the plan now includes Python-based pattern analysis (AI-03, AI-05) running on top of live CRM traffic, a standby server, more concurrent users over time, and modules or features not yet defined. A tower server's RAM ceiling — 128GB — is a real limit if any of that grows. Stepping up to a 2-socket rackmount server now means RAM can simply be added later without replacing the machine.

Spec: Lenovo ThinkSystem SR650 V3 or Dell PowerEdge R750, 128–192GB RAM installed (expandable to 256GB or more), RAID-10 SSD storage around 4TB usable.

A standby server — for hardware failure, not disaster

A second, full copy of the database, kept continuously in sync with the primary via SQL Server's built-in Always On / log shipping features. If the primary fails or needs maintenance, staff can be pointed at the standby within minutes instead of waiting on a restore. Failover is a deliberate, manual action — simpler and cheaper to set up correctly than fully automatic failover, and appropriate for a company this size. Once the primary is repaired, the same reverse-sync pattern used for migration rollback (S-02) brings any changes made on the standby back to the primary.

Staging/test server

A smaller environment to safely validate each module's migration scripts before anything touches real, live data. Its job hasn't changed just because the production servers got bigger — it doesn't need to match their spec, only be realistic enough to catch real problems. A lower-spec physical server or a virtual machine on the core server both work; a VM is the more budget-friendly option now that the core server has real spare capacity to host one.

SQL Server licensing

Missing from earlier drafts of this estimate — worth being direct about that. The standby design (manual failover, one database, no readable secondary) fits entirely within SQL Server Standard Edition's Basic Availability Group limits, so Enterprise Edition's far more expensive per-core licensing isn't required here. Standard Edition can also be licensed as Server + CAL — one server license plus one access license per named user — which is typically cheaper than per-core licensing for a company with a few dozen users rather than thousands. The staging server can run SQL Server Developer Edition at no cost, since it's legitimately non-production use.

Windows Server licensing — or avoid it entirely

SQL Server needs an underlying operating system, and that's a separate license from SQL Server itself. If the servers run Windows Server (the natural pairing given the existing .NET stack), that's a real, additional cost per server. The alternative: SQL Server has run natively on Linux since 2017, fully supported — hosting on Linux instead removes this cost entirely. This is a genuine decision, not an automatic choice either way, since it also affects what your team is most familiar operating day to day.

Server rack & hardware support

Two more physical pieces that hadn't been accounted for. A 2U rackmount server needs an actual rack enclosure to sit in properly — for cooling, cable management, and physical security, not just convenience. Separately, the warranty that comes bundled with a new server isn't the same as an extended support contract (next-business-day parts replacement, phone support) — worth budgeting for a real multi-year support agreement rather than assuming the base warranty covers a production system indefinitely.

Protection built deliberately — since none of it happens invisibly the way it would with a cloud provider.

Power protection

Separate UPS units for the core and standby servers, each sized around 2200–3000VA, with a smaller unit covering staging and networking gear — keeping power protection independent across the critical machines.

Network & remote access

A firewall/VPN appliance (Ubiquiti UniFi Dream Machine Pro, or Fortinet FortiGate 60F) handling both perimeter security and secure remote access for field staff.

Offsite backup

A nightly backup routine with a copy stored off-site, protecting against site-level events a standby server can't cover.

SHEET INF-03 / 04

Security & Monitoring

Mostly configuration, not new purchases — the pieces needed are largely already included in what's already being bought.

Security

  • Encryption in transit — standard TLS/SSL between the browser, API, and database, using free certificates (Let's Encrypt)
  • Encryption at rest — SQL Server's built-in Transparent Data Encryption (TDE), included with SQL Server, just needs to be turned on
  • Role-based access control — enforced at the API layer (S-03): a sales rep's login only ever returns what a sales rep should see
  • Multi-factor authentication — for VPN and admin logins, natively supported by the firewall appliance already in the plan
  • Patch management — a real recurring schedule, tested on staging first before production
  • A password/secrets manager — real credential storage instead of anyone's notes or memory

Monitoring

  • Server health — CPU, RAM, disk, uptime — built into both Lenovo (XClarity) and Dell (iDRAC) server management, no extra cost
  • Database monitoring — SQL Server Agent, included with SQL Server, can alert on issues like low disk space automatically
  • Security monitoring — intrusion detection (IDS/IPS) already included in the firewall appliance
  • Backup verification — an automated alert confirming last night's backup actually completed, not just assumed
  • AI usage monitoring — a spending cap and alert set with the AI provider, so a usage spike is a notification, not a surprise bill
