Database Structure

What the current schema tells us about how the business evolved, and how the redesign fixes it without losing what already works.

What exists today

The current schema is sound in places. Contacts, companies, and activity all follow reasonable relational patterns. The problems are concentrated in three spots.

  • Project ↔ Job overload: a "Job" isn't a separate entity, it's a flag flip on the Projects table. Roughly 30 procurement/contract fields sit unused until that flag flips.
  • Repeating groups: fields like proLoadType1/2/3 and proDeadAns1–7 hard-cap what should be an unlimited child list.
  • Activity scope creep: the activity log carries product-sample fields (actThickness, actPanelColor) that only apply to one specific interaction type.

The repeating load-type and question fields move into proper child tables keyed back to the project, removing the artificial 3-item / 7-item caps. The activity log gets a companion ActivitySampleRequest table so the core log stays generic again. Confirmed with DJ that once a Project becomes a Job, it never reverts back. The lifecycle model only needs to support forward progression, which simplifies the design.

How each module actually gets built

This cycle repeats per-module, four times total.

The cycle for one module (say, Contacts):

  1. Backend: bulk-copy Contacts' existing data into the new, redesigned schema. CDC starts keeping it in sync with the live old system. Reconciliation runs continuously to confirm both stay identical.
  2. API: once Contacts' data is validated, build the API endpoints for it (get/create/update a contact, etc.)
  3. Front end: once the API works, build the new Contacts screens against it
  4. Freeze & cutover: one short scheduled pause, writes point at the new database, the new front end goes live for Contacts specifically

Then the entire cycle repeats for the next module. Full detail on module order and pacing is in S-02.

Technical decision

The current Master Matrix database is a legacy schema that's carried Access-era conventions (like the -1/0 boolean flags) for roughly two decades. The redesign moves to PostgreSQL, hosted on Linux. Both are open-source, with no licensing cost, and a natural fit given the app layer is being rebuilt from scratch rather than staying close to the legacy .NET shape. That's the condition under which moving off SQL Server actually pays off, and it's the condition this project meets.

Known limitation

Historical Project→Job transition dates were never captured, only the current flag state. Migration can backfill a single snapshot per record, not a true history. Future transitions will be fully timestamped going forward.

Migration Strategy

The system is used every day. The plan keeps it fully operational throughout, and lets us prove the new platform works before anyone's workflow depends on it.

A continuous sync, not a cutover night

Rather than a single high-risk migration event, the old database stays live and authoritative while a change-capture process continuously mirrors every update into the new, redesigned schema in the background.

How each module actually cuts over

  • Initial bulk copy: a one-time transformation pass moves everything that already exists in the old table into the new, redesigned schema for that module.
  • CDC + continuous reconciliation take over from there: CDC watches the old database's transaction log and automatically mirrors every live change into the new database from that point forward, while reconciliation runs continuously alongside it, comparing record counts and checksums between both systems and alerting on any drift rather than relying on a one-time check.
  • Rollback safety net: two possible ways to build it. Once a module cuts over, the old database needs to stay caught up in case a rollback is ever needed. Same two options as before apply here, just in reverse: reverse CDC (infrastructure mirrors changes from the new database back to the old one automatically) or dual-write (application code explicitly writes to both). We use reverse CDC, for the same reasoning as the forward direction: no application write logic to touch, and no risk of two writes disagreeing mid-transaction if one succeeds and the other fails.
Technical decision

Freeze is still needed even with CDC and reconciliation running, because CDC always carries a small amount of replication lag, a fraction of a second to a few seconds. A freeze is a short, planned pause that lets that lag drain to zero before writes are pointed at the new database, closing the one window where a write could otherwise be lost.

Business decision

Define an acceptable freeze window for the final, highest-risk cutover (Projects & Jobs) (e.g. end-of-day Friday rather than mid-week) and agree on how far in advance Sales Reps and PMs are told their module is changing underneath them.

Worth holding firm on

No module is considered "cut over" until the reconciliation job has run clean for an agreed validation window. Calendar time here is the cost of doing this safely. Within each module, the sequence is backend → API → front end, each one built and validated before the next begins; across modules, the order is deliberately lowest-risk first (Contacts, then Marketing & Expenses, then Activity, then Projects & Jobs last). Each successful cutover proves the process works before it's applied to the part of the business that matters most.

Technical decision

REST is the default recommendation, since it's simpler to build, test, and reason about for this scope than GraphQL. Framework (e.g. Django REST Framework or Node/Express) should match whatever language the front end and migration scripts are already written in, to minimize context-switching for a small team.

Front-end framework choice follows the API/backend decision above for stack consistency. A modern component framework (e.g. React) is recommended for the UI itself given the responsiveness expected of a daily-use tool.

Business decision

Decide what genuinely needs real-time behavior (activity logging, project status changes) versus what can run as a scheduled batch (leadership reporting exports). This materially changes infrastructure cost and complexity.

Per-module training sessions for sales, PM, and back-office staff, timed to each cutover, plus a named point of contact for support during each module's first few live weeks, when trust in the new system is won or lost.

Why this unlocks the AI ask

An AI agent should never query raw production SQL. Once it calls the same governed endpoints as the front end, "find similar past jobs" or "log this expense" becomes a safe, well-defined action instead of an open-ended risk. See the AI Opportunities tab for what this actually enables.

The final, highest-stakes front-end cutover (Projects & Jobs) is scheduled during the same low-activity freeze window as its data migration counterpart in S-02, so front end and data risk are retired together.

The Bottom Line

The same plan, in plain language.

What we're actually doing

We're replacing the guts of the CRM without turning it off. First we fix how the data is organized, so it isn't fighting itself anymore. Then we build a clean, controlled way for anything (the website used every day, or an AI assistant later) to safely read and update that data. Last, we rebuild the screens people actually look at, matching how the team already works before we change anything about it.

What stays the same, day to day

  • The system keeps working the whole time; nothing goes offline for this to happen
  • Workflows look and feel familiar at first, even though the technology underneath is new
  • Staff get training and a real person to ask, timed to whenever their part of the system actually changes
  • Nothing about how a call, a project, or an expense gets logged changes until staff have been shown the new way

Nothing breaks. Nothing disappears. It just gets easier to use, and ready for what's next, including the AI assistant we talked about.

SHEET T-01 / 03

Getting Started

What can happen in parallel, what's exactly needed to start, and the open question about the existing codebase.

What starts on day one, in parallel

  • Infrastructure procurement and discovery don't depend on each other, so both begin simultaneously. Infrastructure needs just the core server and a staging environment to start; nothing else in the plan (standby server, full UPS, VPN, AI feature access) is needed yet, and follows later, tied to when it's actually required.
  • Discovery means time with the sales, PM, and back-office teams to shadow real workflows, and access to the existing Master Matrix codebase and database for audit.
  • Codebase validation can run alongside both of the above, going through the previously contracted vendor's .NET Core work directly to see what's actually there before committing to any reuse decision, detailed below.

Modules can overlap rather than run fully sequentially. Once a module enters its validation window, work on the next module's backend can begin, since the calendar time in a freeze window is mostly about earning confidence, not full-time engineering effort, so it doesn't block the next module from starting.

The existing codebase, an open question

The previous vendor's engagement was a technical revamp, porting the backend to .NET Core. This proposal starts from a different place, with deep discovery with the sales and PM teams to understand how the business actually works, before any redesign begins. The two approaches may complement each other more than either one alone.

Two possible scenarios, resolved by reviewing the actual code together:

  • If the ported code faithfully preserves working business logic and mainly modernizes the language and runtime, it could meaningfully shorten the API-layer build described in S-03.
  • If it carried forward the same underlying schema issues identified in S-01 (the Project/Job flag, the repeating load-type columns) without addressing them, the core redesign work is largely unaffected either way, since that work is about the data model, not the language it's written in.

SHEET T-03 / 03

Solo Execution

The 9–12 month estimate in T-02 already assumes one technical resource.

The Constraint: One Person, Fixed Hours

A single product manager has a fixed number of hours in a week. Training a module's users, coordinating a freeze window, and starting the next module's backend can all land in the same week, and each one needs dedicated time. The calendar-time overlap described in T-01, where validation windows for different modules run in parallel, shortens the schedule without adding engineering hours. It doesn't create more hours in the week; it just uses the ones already available more efficiently.

The Offset: AI-Assisted Development

AI-assisted development — Cursor or Claude Code, both explicitly supported per the role's own scope — compresses raw coding time for a solo product manager in a way that wasn't possible a few years ago. That doesn't erase the constraint above, but it's a real offset.

If the business wants this meaningfully faster than 9–12 months, the lever is adding a second resource. Worth deciding deliberately.

SHEET INF-01 / 04

Core Server & Staging

Fully on-premises, sized with real headroom — not just for today's CRM, but for what gets added on top of it later. Suggested specs, single planning numbers below.

Why a 2-socket rackmount server, not a basic tower

A single-socket tower server would comfortably handle the CRM database alone. But the plan now includes Python-based pattern analysis (AI-03, AI-05) running on top of live CRM traffic, a standby server, more concurrent users over time, and modules or features not yet defined. A tower server's RAM ceiling (128GB) is a real limit if any of that grows. Stepping up to a 2-socket rackmount server now means RAM can simply be added later without replacing the machine.

Suggested spec: Dell PowerEdge R760 (16th-generation; R750 was 15th-gen and is now superseded), 2x 16-core processors (32 total cores), 128GB DDR5 RAM via 4x 32GB RDIMMs, using only 4 of the chassis's 32 memory slots and leaving 28 open for future growth without replacing anything already installed. RAID-10 storage at 8TB usable (8x 2TB Mixed Use SAS SSDs, 16TB raw), a PERC H755 RAID controller, iDRAC9 for remote management, dual redundant hot-swap power supplies, and a rail kit for the rack enclosure below. Mixed Use drives, not Read Intensive, are a deliberate choice to avoid betting on future write volume being low.

Every component, including the drives, is Dell-branded rather than third-party. Dell's ProSupport can decline to fully cover an issue if a non-Dell component is involved, a real risk for a solo IT person with no backup team to fall back on if something goes wrong. Staying all-Dell keeps the whole system under one support umbrella, at a modest premium over third-party parts.

A standby server, for hardware failure not disaster

A second, full copy of the database, same spec as the core server, kept continuously in sync via PostgreSQL's built-in streaming replication, managed with an open-source tool like Patroni or repmgr. If the primary fails or needs maintenance, staff can be pointed at the standby within minutes instead of waiting on a restore. Failover is a deliberate, manual action, simpler and cheaper to set up correctly than fully automatic failover, and appropriate for a company this size. Once the primary is repaired, the same reverse-sync pattern used for migration rollback (S-02) brings any changes made on the standby back to the primary.

Staging/test server

Runs as a virtual machine on the standby server, not the core server. The standby has the same full spec but is mostly idle, only replicating data rather than serving live queries. Running staging there gets the same $0 additional hardware cost as running it on the core server, without risking a heavy migration-script test competing for resources with real, live production traffic.

Database and OS licensing

The platform decision in S-01 pays off directly here. PostgreSQL is open-source, with no per-core or per-user licensing cost at all, on the primary, the standby, or staging. Pairing it with Linux (Ubuntu Server or Rocky Linux, both free) removes the operating system licensing cost as well — no Windows Server core packs, no CALs.

Server rack & hardware support

A 2U rackmount server needs an actual rack enclosure to sit in properly, for cooling, cable management, and physical security, not just convenience. Separately, ProSupport Plus with 4-Hour Mission Critical is the real support product behind the number below — 24x7 support with a guaranteed 4-hour on-site technician response, not just next-business-day parts replacement or the base warranty a server ships with. Dell's own published upgrade price for this tier is $4,939.38 for a 36-month term, which works out to $137.20/month, or roughly $1,650/year per server, landing very close to the number below.

Power, Network & Backup

Protection built deliberately, since none of it happens invisibly the way it would with a cloud provider.

Power protection

Separate UPS units for the core and standby servers, each an APC Smart-UPS SMT2200C (by Schneider Electric), plus a smaller APC Smart-UPS SMT1500C covering the network appliance (the VPN/firewall), keeping power protection independent across the critical machines. Staging runs as a VM on the standby server, so it's already covered by the standby's own 2200VA unit, not a separate one. Checked against the R760's power specs, a non-GPU configuration like ours realistically draws 200–400W, the same range this sizing was already built on. The R760 is also measurably more power-efficient per unit of work than the R750 it replaced, so no upgrade is needed here after the server model change.

The SMT2200C carries a 3-year repair-or-replace warranty on the unit itself, a separate 2-year warranty on the battery, and a $150,000 Connected Equipment Protection Policy — APC's own guarantee against damage to equipment plugged into it if the UPS fails to do its job.

Offsite backup

A nightly backup routine to Backblaze B2 Cloud Storage, protecting against site-level events a standby server can't cover. Priced per TB stored, which fits a server backup better than a workstation-oriented product. Sized for the server's full 8TB capacity, since that headroom exists partly for a future document archive that could genuinely fill it.

SHEET INF-03 / 04

Security & Monitoring

Mostly configuration. The pieces needed are largely already included in the hardware and software being purchased elsewhere in this proposal.

Security

  • Encryption in transit: standard TLS/SSL between the browser, API, and database, using free certificates (Let's Encrypt)
  • Encryption at rest: disk-level encryption (LUKS, standard on Linux), or PostgreSQL's pgcrypto extension for column-level encryption, both open-source and included
  • Role-based access control: enforced at the API layer (S-03), so a sales rep's login only ever returns what a sales rep should see
  • Multi-factor authentication: for VPN and admin logins, natively supported by the UDM-Pro (INF-02) whether it's purchased separately or bundled through the new ISP
  • Patch management: a real recurring schedule, tested on staging first before production, owned by whoever is doing IT day to day — currently a one-person responsibility
  • A password/secrets manager: for the small number of people who need access to shared admin credentials (database, server, firewall logins), not personal passwords everyone already remembers on their own

Monitoring

  • Server health: CPU, RAM, disk, uptime — built into Dell's iDRAC9 on both the core and standby R760s, no extra cost
  • Database monitoring: pg_cron or standard OS-level scheduled jobs on Linux, open-source, can alert on issues like low disk space automatically
  • Security monitoring: intrusion detection (IDS/IPS) built into the UDM-Pro, same conditional status as MFA above — in place once the VPN/firewall question in INF-02 is resolved
  • Backup verification: an automated alert confirming last night's B2 backup actually completed, not just assumed
  • AI usage monitoring: a spending cap and alert set with the AI provider, so a usage spike is a notification, not a surprise bill

SHEET AI-01 / 05

Find Similar Past Jobs

Type in what a new project looks like, and instantly see every similar job Swirnow has done — going back decades.

The challenge today

When someone's estimating a new project, the only way to remember "didn't we do something like this a few years ago?" is to actually remember it. Twenty years of recorded projects are only useful if someone happens to recall the right example at the right moment.

What this fixes

An estimator asks in plain English: "find similar past jobs", and gets back a real list of comparable projects Swirnow has actually built, instantly. No digging through old files, no relying on memory.

This turns one person's memory into something the whole team can use. New hires get the same institutional knowledge instantly that used to take years to build up.

Why Deals Win or Lose

Decades of "why we lost it" and "why we won it," turned into patterns leadership can actually act on.

What this fixes

Every time a deal is lost or won, the reason gets written down, but nobody's ever had an easy way to look at all of those reasons together. This surfaces the patterns: certain types of projects losing more often, certain stages where deals tend to stall, and more.

This can work two ways: a quarterly trend report for leadership, or a live nudge for sales reps while they're still working a deal. Worth deciding which matters more first.

The pattern-finding itself is standard database analysis: grouping and comparing reasons across every project, run directly on Swirnow's own server. AI is only used at the very end, to turn the finding into a plain-language summary, or to help read reasons that were written as free text instead of picked from a fixed list.

SHEET AI-05 / 05

Know This Client's Slow Spots

Look at everything Swirnow has done with a client before, spot which steps always seem to take them longer, and prepare for it this time.

What this fixes

Some clients are just slower at certain steps: one always takes weeks to sign a contract, another is always late sending drawings. Right now that knowledge lives in whoever's worked with them before. This looks at a client's actual project history and flags their typical slow points before a new project even gets there.

How it plays out

A new project starts with this client. Before the "Contract Sent" stage even begins, the system already knows (from their past three projects) that this stage usually takes them twice as long as most clients. The PM gets a heads-up early, instead of finding out three weeks in that things have gone quiet again.

This gets sharper the more history is available. It works best for repeat clients with a real track record. For a brand-new client, there's nothing to learn from yet, so this feature naturally improves as the new system captures more history over time.
