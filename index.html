Database Structure

What the current schema tells us about how the business evolved, and how the redesign fixes it without losing what already works.

What exists today

The current schema is sound in places — contacts, companies, and activity all follow reasonable relational patterns. The problems are concentrated in two spots, both the result of extending the system reactively over ~20 years rather than remodeling it.

  • Project ↔ Job overload — a "Job" isn't a separate entity, it's a flag flip on the Projects table. Roughly 30 procurement/contract fields sit unused until that flag flips.
  • Repeating groups — fields like proLoadType1/2/3 and proDeadAns1–7 hard-cap what should be an unlimited child list.
  • Activity scope creep — the activity log carries product-sample fields (actThickness, actPanelColor) that only apply to one specific interaction type.

The repeating load-type and question fields move into proper child tables keyed back to the project, removing the artificial 3-item / 7-item caps. The activity log gets a companion ActivitySampleRequest table so the core log stays generic again.

Technical decision

The current Master Matrix database is a legacy schema that's carried Access-era conventions (like the -1/0 boolean flags) for roughly two decades. The redesign moves to PostgreSQL, hosted on Linux — open-source, no licensing cost, and a natural fit given the app layer is being rebuilt from scratch rather than staying close to the legacy .NET shape. That's the condition under which moving off SQL Server actually pays off, and it's the condition this project meets.

Business decision

Confirm with Yvette whether a Job ever reverts to a Project (e.g. a signed contract falls through). If it happens in practice, the lifecycle model needs to support reversal, not just forward progression.

Known limitation

Historical Project→Job transition dates were never captured — only the current flag state. Migration can backfill a single snapshot per record, not a true history. Future transitions will be fully timestamped going forward.

Migration Strategy

The system is used every day. The plan keeps it fully operational throughout, and lets us prove the new platform works before anyone's workflow depends on it.

Approach: continuous sync, not a cutover night

Rather than a single high-risk migration event, the old database stays live and authoritative while a change-capture process continuously mirrors every update into the new, redesigned schema in the background.

Legacy SQL Server
stays live & authoritative
→
Change Data Capture
streams every insert/update
→
New Database
redesigned schema, validated in parallel
Both systems run simultaneously — the new one earns trust before anyone uses it live

Rollout order — lowest risk first

OrderModuleWhy this positionRisk
1Contacts & CompanyFew dependencies, easy to validate independentlyLow
2Marketing & ExpensesSelf-contained, moderate usage volumeMedium
3Activity LogHigh volume, but logic is now well-understoodMedium
4Projects & JobsCore of the business, most complex redesign — moves last, once the pipeline is provenHigh

How each module actually cuts over

  • Initial bulk copy — a one-time transformation pass moves everything that already exists in the old table into the new, redesigned schema for that module.
  • CDC + continuous reconciliation take over from there — CDC watches the old database's transaction log and automatically mirrors every live change into the new database from that point forward, while reconciliation runs continuously alongside it, comparing record counts and checksums between both systems and alerting on any drift rather than relying on a one-time check.
  • Rollback safety net — two possible ways to build it. Once a module cuts over, the old database needs to stay caught up in case a rollback is ever needed. Same two options as before apply here, just in reverse: reverse CDC (infrastructure mirrors changes from the new database back to the old one automatically) or dual-write (application code explicitly writes to both). We use reverse CDC — same reasoning as the forward direction: no application write logic to touch, and no risk of two writes disagreeing mid-transaction if one succeeds and the other fails.
Technical decision

Why freeze is still needed even with CDC and reconciliation running: CDC always has a small amount of replication lag — a fraction of a second to a few seconds. A freeze is a short, planned pause that lets that lag drain to zero before writes are pointed at the new database, closing the one window where a write could otherwise be lost.

Business decision

Define an acceptable freeze window for the final, highest-risk cutover (Projects & Jobs) — e.g. end-of-day Friday rather than mid-week — and agree on how far in advance sales reps and PMs are told their module is changing underneath them.

Non-negotiable

No module is considered "cut over" until the reconciliation job has run clean for an agreed validation window. Calendar time here is the honest cost of doing this safely — it is not something to compress to hit an arbitrary date.

API Layer

The piece that doesn't exist today — a single, governed front door to the data that every future front end, integration, and AI feature builds on.

Why this layer is missing today — and why it matters

The current front end talks directly to the database. Every business rule is scattered across app code, stored procedures, and triggers — which is a large part of why four years of vendor work got stuck: any change to the front end risks the database, and vice versa.

Technical decision

REST is the default recommendation — simpler to build, test, and reason about for this scope than GraphQL. Framework (e.g. Django REST Framework or Node/Express) should match whatever language the front end and migration scripts are already written in, to minimize context-switching for a small team.

Business decision

Decide what genuinely needs real-time behavior (activity logging, project status changes) versus what can run as a scheduled batch (leadership reporting exports) — this materially changes infrastructure cost and complexity.

Why this unlocks the AI ask

An AI agent should never query raw production SQL. Once it calls the same governed endpoints as the front end, "find similar past jobs" or "log this expense" becomes a safe, well-defined action instead of an open-ended risk.

Front End & AI

By this point the hard problems — data integrity, live migration — are solved. The remaining risk is adoption, not architecture.

Principle: replicate first, innovate second

The new interface should feel recognizable on day one — same information, same flow — even though the technology underneath is completely different. Redesigning the workflow and the technology at the same time is a common way modernization projects lose user trust.

Legacy Front End
remaining un-migrated modules
↔
New Front End
migrated modules, built on the API
Both interfaces coexist during the transition, matching the module rollout order from S-02

Where AI adds real value — introduced additively

  • Natural-language project search — "show me projects with GC Turner from last year," translated into the same API calls a person's filters would make.
  • Smart flags — surface contacts with no logged activity in 60+ days, or projects stalled at a status for an unusual length of time.
  • Expense auto-categorization — suggest a category from the description, person still confirms.

Each of these ships as an optional addition next to the existing way of doing things, not a replacement — adoption is earned, not assumed.

Technical decision

Front-end framework choice follows the API/backend decision from S-03 for stack consistency. A modern component framework (e.g. React) is recommended for the UI itself given the responsiveness expected of a daily-use tool.

Business decision

Per-module training sessions for sales, PM, and back-office staff, timed to each cutover — plus a named point of contact for support during each module's first few live weeks, when trust in the new system is won or lost.

Freeze window

The final, highest-stakes front-end cutover (Projects & Jobs) is scheduled during the same low-activity freeze window as its data migration counterpart in S-02 — front end and data risk are retired together, not separately.

SHEET T-01 / 05

Phase Sequencing

What can genuinely happen in parallel, and what needs to happen in order — and why that ordering exists.

What can start immediately, in parallel

  • Infrastructure procurement (S-06's core server, staging environment) and discovery (shadowing sales calls, PM meetings, auditing the existing codebase) don't depend on each other — both can begin on day one.
  • The standby server, full UPS redundancy, VPN, and AI feature buildout are not needed at the start — they can be built out progressively as the project approaches production go-live, not paid for and installed all at once up front.

What has to happen in order, and why

Within each module, the sequence is backend → API → front end, each one built and validated before the next begins — this is what makes each freeze low-risk rather than a leap of faith.

Across modules, the order is deliberately lowest-risk first: Contacts, then Marketing & Expenses, then Activity, then Projects & Jobs last. This isn't caution for its own sake — each successful module cutover proves the entire build-validate-freeze process actually works in practice, so by the time the hardest, highest-stakes module arrives, the team isn't testing the process for the first time on the part of the system that matters most.

Modules can overlap, not just run fully sequentially: once a module enters its validation window, work on the next module's backend can begin — the calendar time in a freeze window is mostly about earning confidence, not full-time engineering effort, so it doesn't block the next module from starting.

SHEET T-03 / 05

The Existing Codebase — An Open Question

Genuinely valuable information the team doesn't have yet — not an assumption in either direction.

What's different about this approach, worth naming clearly

The previous vendor's engagement was a technical revamp — porting the backend to .NET Core. This proposal starts from a different place: deep discovery with the sales and PM teams to understand how the business actually works, before any redesign begins. The two approaches may complement each other more than either one alone.

Why a timeline impact can't be estimated yet

Two honest, realistic scenarios, and there's no way to know which applies without reviewing the actual code:

  • If the ported code faithfully preserves working business logic and mainly modernizes the language and runtime, it could meaningfully shorten the API-layer build described in S-03.
  • If it carried forward the same underlying schema issues identified in S-01 (the Project/Job flag, the repeating load-type columns) without addressing them, the core redesign work is largely unaffected either way — that work is about the data model, not the language it's read in.

Recommendation: reviewing this code is the first concrete action item of Phase 1, before finalizing any timeline commitment beyond the preliminary estimate in T-04. A short, focused audit — not a full commitment either way — is enough to know which scenario applies.

Solo Execution

The 9–12 month estimate in T-04 already assumes one technical resource, not a team — worth stating that plainly rather than leaving it implicit.

Working against the timeline

One person can't parallelize effort the way a team could. If training a module's users, coordinating a freeze window, and starting the next module's backend all need real hours in the same week, that's genuine contention — not something the module overlap described in T-01 fully solves, since that reasoning assumes calendar-time overlap (waiting during another module's validation window), not effort-time overlap (actively working on two things at once).

Working for the timeline

AI-assisted development — Cursor or Claude Code, both explicitly supported per the role's own scope — genuinely compresses raw coding time for a solo developer in a way that wouldn't have been true even a few years ago. That doesn't erase the constraint above, but it's a real, legitimate offset, not hand-waving.

If the business wants this meaningfully faster than 9–12 months, the lever isn't compressing one person's work further — it's adding a second resource. Worth deciding deliberately, not assuming either way.

Find Similar Past Jobs

Type in what a new project looks like, and instantly see every similar job Swirnow has done — going back decades.

The problem today

When someone's estimating a new project, the only way to remember "didn't we do something like this a few years ago?" is to actually remember it. Twenty years of recorded projects are only useful if someone happens to recall the right example at the right moment.

What this fixes

An estimator asks in plain English — "find similar past jobs" — and gets back a real list of comparable projects Swirnow has actually built, instantly. No digging through old files, no relying on memory.

This turns one person's memory into something the whole team can use — new hires get the same institutional knowledge instantly that used to take years to build up.

Why Deals Win or Lose

Decades of "why we lost it" and "why we won it" — turned into patterns leadership can actually act on.

What this fixes

Every time a deal is lost or won, the reason gets written down — but nobody's ever had an easy way to look at all of those reasons together. This surfaces the patterns: certain types of projects losing more often, certain stages where deals tend to stall, and more.

This can work two ways — a quarterly trend report for leadership, or a live nudge for sales reps while they're still working a deal. Worth deciding which matters more first.

The pattern-finding itself is standard database analysis, not AI — grouping and comparing reasons across every project, run directly on Swirnow's own server. AI only gets used at the very end, to turn the finding into a plain-language summary, or to help read reasons that were written as free text instead of picked from a fixed list.

Know This Client's Slow Spots

Look at everything Swirnow has done with a client before, spot which steps always seem to take them longer, and prepare for it this time.

What this fixes

Some clients are just slower at certain steps — one always takes weeks to sign a contract, another is always late sending drawings. Right now that knowledge lives in whoever's worked with them before. This looks at a client's actual project history and flags their typical slow points before a new project even gets there.

How it plays out

A new project starts with this client. Before the "Contract Sent" stage even begins, the system already knows — from their past three projects — that this stage usually takes them twice as long as most clients. The PM gets a heads-up early, instead of finding out three weeks in that things have gone quiet again.

SHEET INF-01 / 04

Core Server & Staging

Fully on-premises, sized with real headroom — not just for today's CRM, but for what gets added on top of it later. Specs locked, single planning numbers below, not ranges.

Why a 2-socket rackmount server, not a basic tower

A single-socket tower server would comfortably handle the CRM database alone. But the plan now includes Python-based pattern analysis (AI-03, AI-05) running on top of live CRM traffic, a standby server, more concurrent users over time, and modules or features not yet defined. A tower server's RAM ceiling — 128GB — is a real limit if any of that grows. Stepping up to a 2-socket rackmount server now means RAM can simply be added later without replacing the machine.

Locked spec: Dell PowerEdge R760 (16th-generation — R750 was 15th-gen and is now superseded), 2x 16-core processors (32 total cores), 128GB DDR5 RAM via 4x 32GB RDIMMs — using only 4 of the chassis's 32 memory slots, leaving 28 open for future growth without replacing anything already installed. RAID-10 storage at 8TB usable (8x 2TB Mixed Use SAS SSDs, 16TB raw), a PERC H755 RAID controller, iDRAC9 for remote management, dual redundant hot-swap power supplies, and a rail kit for the rack enclosure below. Mixed Use drives, not Read Intensive — a deliberate choice to avoid betting on future write volume being low.

Every component, including the drives, is Dell-branded rather than third-party. Dell's ProSupport can decline to fully cover an issue if a non-Dell component is involved — a real risk for a solo IT person with no backup team to fall back on if something goes wrong. Staying all-Dell keeps the whole system under one support umbrella, worth the modest premium over mixing in cheaper third-party parts.

A standby server — for hardware failure, not disaster

A second, full copy of the database, same spec as the core server, kept continuously in sync via PostgreSQL's built-in streaming replication, managed with an open-source tool like Patroni or repmgr. If the primary fails or needs maintenance, staff can be pointed at the standby within minutes instead of waiting on a restore. Failover is a deliberate, manual action — simpler and cheaper to set up correctly than fully automatic failover, and appropriate for a company this size. Once the primary is repaired, the same reverse-sync pattern used for migration rollback (S-02) brings any changes made on the standby back to the primary.

Staging/test server

Runs as a virtual machine on the standby server, not the core server — the standby has the same full spec but is mostly idle, only replicating data rather than serving live queries. Running staging there gets the same $0 additional hardware cost as running it on the core server, without risking a heavy migration-script test competing for resources with real, live production traffic.

Database and OS licensing — $0

The platform decision in S-01 pays off directly here. PostgreSQL is open-source, with no per-core or per-user licensing cost at all, on the primary, the standby, or staging. Pairing it with Linux (Ubuntu Server or Rocky Linux, both free) removes the operating system licensing cost as well — no Windows Server core packs, no CALs.

Server rack & hardware support

A 2U rackmount server needs an actual rack enclosure to sit in properly — for cooling, cable management, and physical security, not just convenience. Separately, ProSupport Plus with 4-Hour Mission Critical is the real support product behind the number below — 24x7 support with a guaranteed 4-hour on-site technician response, not just next-business-day parts replacement or the base warranty a server ships with. The breakdown: Dell's own published upgrade price for this tier is $4,939.38 for a 36-month term, which works out to $137.20/month, or roughly $1,650/year per server — landing very close to the number below.

Power, Network & Backup

Protection built deliberately — since none of it happens invisibly the way it would with a cloud provider.

Power protection

Separate UPS units for the core and standby servers, each an APC Smart-UPS SMT2200C (by Schneider Electric), plus a smaller APC Smart-UPS SMT1500C covering staging and networking gear — keeping power protection independent across the critical machines. Re-checked against the R760's actual power specs: a non-GPU configuration like ours realistically draws 200–400W, the same range this sizing was already built on, and the R760 is measurably more power-efficient per unit of work than the R750 it replaced — so no upgrade needed here after the server model change.

The SMT2200C carries a 3-year repair-or-replace warranty on the unit itself, a separate 2-year warranty on the battery, and a $150,000 Connected Equipment Protection Policy — APC's own guarantee against damage to equipment plugged into it if the UPS fails to do its job.

Offsite backup

A nightly backup routine to Backblaze B2 Cloud Storage, protecting against site-level events a standby server can't cover — priced per TB actually stored, not per computer, which fits a server backup far better than a workstation-oriented backup product. Sized for the server's full 8TB capacity, not just today's actual data usage, since that headroom exists partly for a future document archive that could genuinely fill it.

AI feature usage

Pay-per-use, scaling directly with actual usage — estimated for moderate use by ~20–40 staff.

SHEET INF-03 / 04

Security & Monitoring

Mostly configuration, not new purchases — the pieces needed are largely already included in what's already being bought.

Security

  • Encryption in transit — standard TLS/SSL between the browser, API, and database, using free certificates (Let's Encrypt)
  • Encryption at rest — disk-level encryption (LUKS, standard on Linux), or PostgreSQL's pgcrypto extension for column-level encryption, both open-source and included
  • Role-based access control — enforced at the API layer (S-03): a sales rep's login only ever returns what a sales rep should see
  • Multi-factor authentication — for VPN and admin logins, natively supported by the UDM-Pro (INF-02) whether it's purchased separately or bundled through the new ISP
  • Patch management — a real recurring schedule, tested on staging first before production, owned by whoever is doing IT day to day — currently a one-person responsibility, worth keeping realistic rather than assuming a team's worth of coverage
  • A password/secrets manager — real credential storage instead of anyone's notes or memory

Monitoring

  • Server health — CPU, RAM, disk, uptime — built into Dell's iDRAC9 on both the core and standby R760s, no extra cost
  • Database monitoring — pg_cron or standard OS-level scheduled jobs on Linux, open-source, can alert on issues like low disk space automatically
  • Security monitoring — intrusion detection (IDS/IPS) built into the UDM-Pro, same conditional status as MFA above — in place once the VPN/firewall question in INF-02 is resolved
